# Этапы 16–17. Управление пользователями и роль `platform_admin`

## Admin API

| Method | Endpoint | Назначение |
|---|---|---|
| GET | `/api/v1/admin/users` | список локальных пользователей |
| POST | `/api/v1/admin/users` | создать пользователя, пароль и роль |
| PATCH | `/api/v1/admin/users/{username}` | изменить роль и/или деактивировать пользователя |

Доступ имеют только `model_governance` и `platform_admin`. Удаление не
реализовано: деактивация сохраняет историю и не разрушает audit trail.

## Роль `platform_admin`

При старте создаётся локальная демонстрационная учётная запись
`demo_platform_admin`. `platform_admin` может выполнять admin endpoints, но
все действия оставляют persistent audit event с actor, предыдущим/новым
состоянием и причиной изменения.

## Интерфейс администрирования и workflow-контроли

Экран React **Administration** выводит таблицу локальных пользователей с
именем, ролью, статусом и датой создания, а также отдельные формы создания
пользователя и изменения доступа. Для изменения доступа обязательны текстовое
обоснование и явное подтверждение действия.

Контроль реализован на двух уровнях: интерфейс делает правила видимыми, а
backend остаётся источником истины и отклоняет self-escalation, изменения без
подтверждения, а также деактивацию или понижение последнего активного
`platform_admin`. Деактивированная учётная запись не может получить новый
access token. События `user_created` и `user_access_updated` сохраняются
в `audit_events`. Это контроль исследовательского прототипа, не замена
корпоративной системе управления идентификацией.

Endpoints также доступны для инспекции в Swagger по адресу
`http://localhost:8000/docs`.
